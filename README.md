# 录音棚跳线盘路由规划器

一个跳线盘（Patchbay）路由规划网页应用：配置设备端口、背板连接与常态模式，
指定若干条“信号源 → 目标设备”的路由，系统自动计算**前面板最少跳线方案**，
正确处理插头对常态连接的断开规则，检测反馈环路，并在页面上绘制信号链、
列出接线顺序；无解路由会标明冲突端口。

新增 **单点故障评估（断路演练）** 模块：完成规划后，可任选一条**已安装跳线**
或一条**生效中的常态连接**模拟断路，后端在保持其他占用状态不变的前提下重新评估
全部路由，列出受影响路由、失效原因、断点端口与仍可用的替代路径；候选断点按
受影响路由数量降序排列。

新增 **前面板走线排版** 模块：完成规划后，用户为面板分区指定**可用走线槽层**
与**固定插孔列位**；系统保持信号拓扑、常态模式与跳线端点不变，为每根跳线分配
**走线层**与**左右绕行方向**，按「交叉数最少 → 跨区线数最少 → 同层长度最短」
字典序求解，输出每根跳线的层/方向、交叉对与无法避免的冲突；页面展示优化前后
指标与可缩放面板走线图。

新增 **信号命名一致性审计** 模块（`POST /api/signal-audit`）：用户为设备端口、
插孔对、已规划跳线与路由填写**规范信号名**及**别名**；系统沿设备内部、生效常态
与已安装跳线传播名签，按**半常态分流语义**归并端点，检测：

- **互斥名称（mutex）**：同一物理连通分量上出现多个规范信号名；
- **别名环（alias-ring）**：别名指向成环（`cycle`）或同一别名被指向多个规范名
  （`diverging` 分叉）；
- **无标签断点（unlabeled）**：承载路由信号的跳线源端、以及半常态上插孔插线
  的并送分流点没有任何名签；
- **跨路由串线（crosstalk）**：来自**独立信号源**（与名签无关）的已规划路由在
  同一物理连通分量汇合。信号源身份即路由源端口：同源端口、反馈环中互达的源端口
  合并为一个独立源；审计还会从路由源沿设备内部、生效常态与跳线**反向追溯共同
  上游**——一个真实信号进入多输出设备后从两个输出端口分别建立路由（或被常态 /
  跳线推动出的多条支路）只算该独立源的**同源分支**，归为同一来源、不计串线；
  只有反向终源互不相同的多源混合（含调音台混合输出、半常态并送汇合）才报警。
  **改名 / 改别名不会消警**，只有调整路由规划或物理连通后重新规划才能消除。

每个问题都给出**多源 BFS 最短证据路径**（port/edge 交替，含设备内部 / 常态 /
跳线各跳）、**可采纳规范名**（分量内声明次数最多，并列取字典序最小）与一组
**修正预览**（把落败名降级为别名的 `rename`、补名签的 `add-label`、剪断环边的
`break-alias`）；**跨路由串线不提供可消警的改名操作**，只返回物理处置提示，复审
时仍高亮同一条物理证据路径。审计**只读取规划结果，不修改任何路由 / 常态 / 跳线**；
页面按连通分量着色拓扑，点击问题高亮其最短证据路径，可逐条采纳修正预览并即时复审。

新增 **无中断改线演练**（`POST /api/seamless-rewire`）：操作员提交**当前配置**、
**目标路由列表**（设备与插孔对不变，只换路由）与**必须始终保持通声的当前路由
序号**。后端先按当前配置重建全部已安装跳线，再用同一份设备 / 插孔对对目标路由做
一次全新规划，随后在「现状接线 → 目标接线」之间用带保护约束的确定性搜索
（Dijkstra）生成逐步方案：

- **拆线（remove）**：跳线两端全部拔下；**换接（complete）**：跳线一端保持、
  另一端改插空闲插孔（含为解开占用死锁的**临时让位 park**）；**补线（add）**：
  在两个空闲插孔间插线——**优先复用此前拆下的兼容跳线**，其次才动用新跳线；
- **临时跳线（temp-add / temp-remove）**：仅过渡存在、目标态不需要的旁路跳线，
  端点只能取**目标态也空闲**的插孔（故永不与目标补线抢孔），单独编号、单独列出；
- 每一步恰含**两个插 / 拔动作**，搜索在**每个动作完成后的中间快照**上都按
  **全常态（任一侧插线即断）/ 半常态（仅下孔插线断、上孔插线并送）/ 直通**
  规则由当前插头占用直接推导物理图，校验每个保护路由 source→target 仍有
  完整通路（设备内部 + 生效常态 + 在役跳线）。典型反例：换接只能“先拔旧端、
  再插新端”，拔下后悬空的跳线不成回路——若保护路由只依赖这一根跳线，该
  瞬间必失声，此顺序直接拒绝；补线 / 拆线两个动作可换序时，搜索会选取两个
  中间快照都通声的次序（例：向全常态下插孔补线前，先把跳线另一端插上，
  让新通路先建立）。逐步输出**按实际操作次序的插孔变更、每个中间快照的
  前面板图（悬空插头单独标注）、受影响路由、保护路由是否仍可用（含其当前
  通路与是否经临时跳线）**；
- 优化目标字典序：**步骤数最少（拆装次数最少）→ 优先完工 / 补线 / 拆线（驱动
  兼容跳线复用）→ 最后动用临时旁路**；搜索节点超限时返回 `inconclusive` 说明，
  不伪称证明无解；
- **若不存在保持保护路由连续通声的顺序**：返回 409 与结构化阻塞原因
  （`jack-occupied` 占用死锁插孔、`must-remove-cable` 必拆保护跳线、
  `must-break-normal` 必断保护常态、`no-bypass-jack` 无空闲旁路插孔、
  `protected-silent-baseline` 保护路由现状即失声），**不产生任何步骤**；
- **目标配置非法**（端口引用错误、目标路由无解、目标跳线就位后仍不通声等）
  一律 400，同样**不产生半成品方案**。

页面「7. 无中断改线演练」卡片提供目标路由编辑表（可一键同步当前路由）、当前路由
保护勾选与**逐步操作预览**（点击每一步查看按实际次序排列的两个插 / 拔动作、
每个动作完成后的中间快照前面板图（悬空单端用空心线头标注）、受影响路由、保护
路由通声状态与整步完成后的状态；临时跳线用黄色虚线标注），并汇总拆线 / 换接 /
补线 / 临时跳线 / 新跳线 / 复用计数与跳线复用清单。

新增 **串音隔离规划** 模块（`POST /api/crosstalk-isolation`）：用户为每条路由
填写一个**隔离组**（同名组允许共线、留空不参与隔离），并声明**不得互相连通的
组对**。系统按全常态 / 半常态 / 直通语义对**全部路由重新规划**：

- **隔离判据**：规划完成后的无向物理连通分量（设备内部连接 + 生效常态 + 前面板
  跳线，半常态上插孔插线的并送汇合也在其中）上，禁配组各自的路由链路端口不得
  落入同一分量；
- **搜索策略**：先做输入顺序贪心对照（与原规划同一逐条最短路模型）；贪心不满足
  时在「下一条规划哪条路由 × 该路由走哪条候选路径」两层上做**带回溯的深度优先
  搜索**——会**回溯重排已规划路由**，也会为后续路由改走多用跳线的替代路径
  （候选路径为有界环无关路径枚举，按跳线数升序）。优化目标字典序：全部路由可通
  → **跳线总数最少**（迭代加深 0,1,2,…）→ 规划顺序尽量贴近输入顺序；
- **剪枝**：设备内部边与已安装跳线只会增加，在这两类边构成的「永久图」上一旦
  禁配组共分量，该分支直接剪除；任一条剩余路由在当前状态下已无通路（占用与常态
  保护单调增长）即剪除；
- **反馈环路检测保留**：隔离方案完成后仍在有向信号流图上检测并返回反馈环
  （警告，不使方案失效）；
- **无解**：穷尽回溯后仍有禁配组无法分离时返回 **409 `ISOLATION_CONFLICT`**，
  给出冲突组对、组对之间在「终止状态实际边 + 未提交路由理想路径边」并集图上的
  **多源 BFS 最短共享证据**（设备内部 / 常态 / 跳线逐跳；共享背板插孔这类物理
  上只能插一根跳线的资源冲突标记为 `structural`）、**未满足路由**及原因、
  输入顺序贪心对照拓扑——**不返回任何接线步骤，不提交部分方案**；搜索超过节点
  上限时返回 `inconclusive`，不伪称证明无解；
- 隔离声明本身非法（组数量与路由数不符、自禁配、引用未使用的组等）返回
  **400 `ISOLATION_INVALID`**。

页面「8. 串音隔离规划」卡片提供按路由填写隔离组的表格、禁配组对的增删与隔离组
概览；成功时展示隔离组 → 物理分量映射、最少跳线接线顺序、每条路由的链路
（含隔离组色标、规划步序、所属分量）与**按分量着色 / 按隔离组描边的拓扑图**；
无解时展示冲突组对卡片（点击在拓扑图上**高亮最短共享证据**）、未满足路由清单、
终止状态拓扑（红色描边冲突端点、黄色粗线证据）与输入顺序贪心失败对照拓扑。

- 后端：Python Flask（`app.py` + 纯逻辑求解器 `solver.py`）
- 前端：原生 HTML / CSS / JavaScript（`static/`）

## 快速开始（Docker，单条命令）

```bash
docker compose up --build
```

启动后在浏览器访问：**http://localhost:8000**

## 本地开发（不用 Docker）

```bash
pip install -r requirements.txt
python app.py
```

同样访问 **http://localhost:8000**。

## 使用说明

1. **设备与端口**：登记每台设备的输入/输出端口（逗号分隔）。
2. **插孔对与背板连接**：每对插孔包含上插孔 `编号T`（背板接设备输出）与
   下插孔 `编号B`（背板接设备输入），并选择常态模式：
   - **全常态（full）**：上/下插孔任意一侧插入插头即断开常态连接；
   - **半常态（half）**：仅下插孔插入断开常态；上插孔插入时常态保持、信号并送（可监听/分流）；
   - **直通（through）**：上下插孔之间无常态连接。
3. **路由请求**：按顺序指定多条“输出端口 → 输入端口”的路由。
4. 点击 **计算路由方案**，页面展示：
   - 最少跳线数量与**接线顺序**；
   - 每条路由的**信号链**（常态 / 设备内部 / 跳线逐段展示）；
   - **前面板跳线图**（生效/断开的常态、跳线走线）；
   - 插头对常态连接的影响说明；
   - 无解路由的**冲突端口**（插孔被占用、常态被保护等）；
   - **反馈环路**警告（信号经设备与连线形成回路时）。

右上角下拉框可载入八个内置示例：标准录音链（可解）、冲突演示（无解）、
反馈环路演示、走线排版演示（多分区 + 交叉优化）、无中断改线演练演示（拆线 /
换接 / 补线 + 保护路由不中断）、命名审计演示（四类命名问题）、
串音隔离演示（贪心失败 → 回溯重排 / 替代路径）、
关键路由双通道演示（主备抗单点断路 + 半常态并送 / 热备）。

## 单点故障评估（断路演练）

1. 先点击 **计算路由方案** 完成一次正常规划；规划结果里的所有**已安装跳线**
   与**生效中的常态连接**会进入“4. 单点故障评估”卡片的下拉清单，并
   **按受影响路由数量降序排列**（数量相同时跳线在前、再按编号）。
2. 选择一个断点后点击 **🔌 断路演练**，后端会：
   - 摘除该跳线（释放其两端插孔）或将该常态连接强制切断，**其余跳线与
     常态占用一律保持不变**；
   - 按原路由顺序对受影响路由重新求最短路（只允许使用当前空闲插孔插入
     新跳线，不改动任何仍在服役的连接）；
   - 返回受影响路由、失效原因、**断点端口**（如 `3T / 3B`）、仍可用的
     **替代路径信号链**、需要新增的跳线与替代接线顺序，以及断路后的面板图；
   - 未受影响路由原样列出（沿用原跳线/常态）。
3. 结果区按“失效路由优先、其后按路由编号”排序；页面底部给出所有断点的
   单点故障排序总表。

演练语义说明：不存在全局重排——替代路径必须与其余仍在服役的路由共存
（与原规划一致的逐条贪心模型）；若某条路由在其他占用不变时确实无路可走，
接口返回 **409** 结构化结果，完整评估数据仍在响应体的 `assessment` 字段中。
注意：半常态（half）插孔在上插孔插线时信号并送，多个路由可共享同一条常态，
因此同一次断路可能同时影响多条路由。

## 前面板走线排版

完成一次 **计算路由方案** 后，“5. 前面板走线排版”卡片出现（规划无解时仍可对
已安装的跳线排版）。为每个分区填写：

- **插孔列位**：该分区内插孔对编号，按从左到右的物理顺序填写；所有插孔对必须
  且只能属于一个分区（后端校验，漏列/重列/未知编号都会 400 报错）；
- **可用走线槽层**：整数编号列表，如 `1, 2`；也可带容量 `1:6, 2:4`
  （每层每分区容量默认 8）。槽层深度按首次出现顺序确定，编号越小越靠近面板。

点击 **🧵 计算走线排版**，后端先复用既有规划（**信号拓扑、常态模式、跳线端点
完全不变**），再做排版：

- 跳线从上行 T 插孔垂入走线槽，水平走到下行 B 插孔后升起；跳线水平跨度经过的
  每个分区都必须提供同一槽层（**公共槽层**），并占用各分区该层 1 个容量；
- 为每根跳线分配槽层与**左右绕行方向**（决定从哪一侧进入相邻列槽隙）；
- 优化目标按字典序：**交叉数最少 → 跨区线数最少 → 同层长度最短**；
- 同层相邻列跳线的进槽方向对撞通过方向调整消除（不算冲突），反向绕行有 0.5
  列距的长度附加；
- **无法避免的冲突**：无公共槽层或容量已满导致的跳线未分配；以及受公共槽层/
  容量限制、改层也无法减少交叉的残留同层交叉（逐对给出交叉跳线号、槽层与
  `unavoidable` 判定）。

页面输出：优化前（贪心基线）/ 优化后的**指标对照表**（交叉数、跨区线数、
同层总长度、方向对撞、未分配跳线）、**每根跳线的走线方案表**（层/方向/长度/
是否跨区/状态）、冲突清单与**可缩放面板走线图**（±/复位缩放，槽层容量、
绕行方向、红色 ✕ 交叉点、红色虚线未分配跳线均有标注）。

> 关于“跨区线数最少”：分区列位由用户固定后，一根跳线是否跨区只取决于其两个
> 端点，因此该指标在排版过程中是**定值**，仅在交叉数并列时作为次序参考；它仍
> 是求解顺序中的第二优先级并在前后指标中如实展示。槽层与容量受限时的首要目标
> 是把每根跳线都分配出去（未分配数最少），其次才是交叉数等三项。

## 信号命名一致性审计

完成一次 **计算路由方案** 后，“6. 信号命名一致性审计”卡片出现（规划无解时
仍可对物理图与已安装跳线审计）。四个标签页分别为**设备端口 / 插孔对 / 已安装
跳线 / 路由**填写名签，每行一个**规范信号名**与一个**别名**（均选填）。载入
“命名审计演示”示例会预填一套覆盖四类问题的名签。

点击 **🔎 运行命名审计**，后端先复用既有规划（不改动任何路由结论），再：

- 在「设备内部 + 生效常态 + 已安装跳线」**无向物理图**上求连通分量；
- 把名签沿边传播：规范名落到端口；**别名按“别名 → 规范名”声明构造有向图**
  解析（纯别名端口在唯一收敛时按目标规范名补全）；
- 按**半常态分流语义**归并：半常态上插孔插线时常态保持、信号并送，上/下端口
  仍属同一分量，该点额外视为需要命名的**分流点**；
- 输出四类问题，每条含 `severity`、`component`、涉及名称 `names`、
  `suggestedName`（串线无此字段）、`evidence`（最短证据路径）与 `fixes`
  （修正预览；串线为**空数组**，改由 `resolution` 给出物理处置提示）。

| 问题类型 | code | 含义 | 修正预览 |
| --- | --- | --- | --- |
| 互斥名称 | `mutex` | 同一连通分量有多个规范名 | `rename`：落败名降为别名，统一为建议名 |
| 别名环 | `alias-ring`（`subtype: cycle/diverging`） | 别名指向成环或一别名对多规范名 | `break-alias`：剪断环边并统一规范名 |
| 无标签断点 | `unlabeled`（warning） | 路由跳线源端 / 半常态并送分流点无名签 | `add-label`：沿用分量内唯一规范名补签 |
| 跨路由串线 | `crosstalk` | 来自**独立信号源**的已规划路由汇于同一物理分量（与规范名/别名无关） | **无 rename**：只能改路由规划或断开物理连通，复审仍高亮同一证据路径 |

页面输出：统计条（分量数与四类问题计数）、**问题清单卡片**（点击展开最短证据
路径与可逐条采纳的修正）、**按连通分量着色的审计拓扑图**（点击问题后黄色高亮
证据路径、红色描边冲突端点，常态 / 跳线 / 半常态并送均有图示）。采纳任一修正
只会回填上方名签输入框并**立即重新审计**，不会修改路由；也可一键清空名签。

> 审计是只读分析：它不改配置、不重路由、不写入任何状态，结果完全由当前
> `config` + `labels` 决定；可反复运行。原规划、断路演练与走线排版互不影响。

## API

- `GET /` — 页面
- `GET /api/examples` — 内置示例配置
- `POST /api/plan` — 求解（原有规划流程，保持可用），请求体：

```json
{
  "devices": [{"name": "PRE", "inputs": ["in"], "outputs": ["out"]}],
  "pairs":   [{"id": 1, "top": "MIC.out", "bottom": "PRE.in", "mode": "half"}],
  "routes":  [{"source": "MIC.out", "target": "PRE.in"}]
}
```

返回跳线清单、接线顺序、每条路由的信号链、冲突与反馈环路，以及
`failurePoints`（可演练断点及其受影响路由数，已排序）。

- `POST /api/fault-drill` — 单点故障断路演练，请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "target": { "type": "normal", "id": 3 }
}
```

`target.type` 为 `cable`（已安装跳线，`id` 为跳线编号）或 `normal`
（生效常态，`id` 为插孔对编号）。200 响应包含 `affectedRoutes`
（`restored`：替代链/新增跳线；`unroutable`：失效原因与断点端口）、
`unaffectedRoutes`、`breakPorts`、`newCables`、`steps`、断路后的
`pairs` / `cables` / `feedbackLoops` 与 `failurePoints` 排序表；
409 时上述结构位于响应体 `assessment` 中。

- `POST /api/panel-layout` — 前面板走线排版，请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "layout": {
    "zones": [
      { "name": "左区", "columns": [1, 2, 3],
        "layers": [1, 2, {"id": 3, "capacity": 6}] }
    ]
  }
}
```

`columns` 是插孔对编号从左到右的物理列位（必须覆盖全部插孔对且不重复）；
`layers` 为该分区可用走线槽层，可写整数或 `{id, capacity}`（容量默认 8）。
响应包含：

- `zones`：各分区列位区间、槽层深度与 `used/capacity` 占用；
- `jacks`：每个插孔的列位/分区/端口（供绘图）；
- `cables`：每根跳线的 `layer`、`direction`（`L` 左绕 / `R` 右绕）、
  `directionLabel`、`fromCol/toCol`、`fromZone/toZone`、`crossZone`、
  `length`、`status`（`routed` / `unassigned`）与未分配原因；
- `crossingPairs`：优化后仍残留的同层交叉对（含 `unavoidable` 判定）；
- `conflicts`：无法避免的冲突（`unassigned` / `crossing`）及中文原因；
- `metrics.baseline` 与 `metrics.optimized`：优化前后的 `crossings`、
  `crossZone`、`length`、`gapConflicts`、`unassigned`；
- `planOk`（原规划是否全部可解）、`solverNote`（搜索超限时的回退说明）。

排版接口不改动任何路由结论：它内部复用 `POST /api/plan` 的同一规划流程，
原规划冲突时仍可对已安装跳线排版，并以 `planOk`/横幅提示。

- `POST /api/signal-audit` — 信号命名一致性审计（只读，不改路由），请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "labels": {
    "ports":  [ {"port": "MIC.out", "name": "VOX", "alias": "人声"} ],
    "pairs":  [ {"id": 1, "name": "VOX"} ],
    "cables": [ {"id": 2, "name": "VOX"} ],
    "routes": [ {"index": 0, "name": "VOX"} ]
  }
}
```

`labels` 的四个数组均选填，每项只需 `name`（规范信号名）与 `alias`（别名）
至少一个；`ports[].port` 为 `设备.端口`，`pairs/cables` 用编号 `id`
（cable 必须是当前规划已安装的跳线），`routes` 用从 0 起的 `index`。
插孔对 / 路由名签会同时挂到其两端端口。响应包含：

- `ok`：是否不存在 error 级问题（unlabeled 为 warning，不影响 ok）；
- `planOk`：底层规划是否全部可解；
- `summary`：`components` / `activeComponents`（承载路由的分量）/
  `labeledPorts` / `issueCounts`（四类计数）/ `issueTotal`；
- `components[]`：每个连通分量的端口（含插孔 `jack`、是否被命名 `labeled`）
  与归并出的 `canonicalNames`，供前端按分量着色；
- `issues[]`：`type`（mutex/alias-ring/unlabeled/crosstalk）、`severity`、
  `subtype`（alias-ring 的 cycle/diverging）、`component`、`names` /
  `conflictingNames` / `preferredName`、`suggestedName`、`routes`、
  `aliasChain`（环）、`evidence`（port/edge 交替的最短证据路径，每个 port
  带 `jack` 与该点 `names`，每条 edge 带类型与中文 label）、`fixes[]`；
  crosstalk 的 `fixes` 恒为 `[]`（改名不能消警），其 `names` 为两端独立源
  端口（与标签无关、供排序），另带 `sources`（两组独立源：`port`/`ports`
  /`originPorts`（反向追溯到的共同上游终源端口；同源分支可能与其直接源端口
  不同）/`routes`）、`routesBySource`（源端口 → 归属路由）、`downstream`（由多路
  并流形成的下游混合点，如调音台混合输出）与 `resolution`（仅物理处置提示）；
  同源多输出分支不会产生串线条目，复审时也不再提示改路由或断开这些分支；
  串线证据路径只随规划/物理连通改变，复审时保持不变。
- `fixes[]`：`action` 为 `rename`（`fromName→toName`，原名入 `alias`）、
  `add-label`（`name` 为建议补签名，可能为 null 需人工指定）或
  `break-alias`（删除 `removedAlias`、统一 `name`），均带 `target`
  （kind/id/index/port）与中文 `label`；crosstalk 不返回任何 fix。
- `pairs` / `cables` / `routes`：审计所基于的规划拓扑（供绘图与复核）。

- `POST /api/seamless-rewire` — 无中断改线演练，请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "targetRoutes": [
    {"source": "MIC.out", "target": "MON.in1"}
  ],
  "protectedRoutes": [0, 1]
}
```

`targetRoutes` 使用与 `config` 相同的设备 / 插孔对（不允许改背板）；
`protectedRoutes` 为**当前路由从 0 开始的序号**，这些 `(source,target)` 对必须也
原样出现在目标路由中。200 响应包含：

- `steps[]`：逐步方案，每项含 `seq` / `action`（`remove` 拆线 / `complete` 换接 /
  `park` 临时让位 / `add` 补线 / `temp-add`、`temp-remove` 临时跳线）/ `summary`、
  `cable`、`jackChanges`（按**实际操作次序**排列的两个插/拔动作，带 `order`
  1/2 与 `plug`/`unplug`）、`microOps[]`（**每个插/拔动作一项**：`op` 次序、
  `jack`/`change`、该动作后每条保护路由的 `protected[].audible`、
  `protectedAllAudible` 与中间快照 `snapshot`——快照含 pairs/cables 与
  `pendingPlugs`，悬空单端跳线在 cables 中带 `dangling: true` 且另一端为
  null）、`affectedRoutes`（前后通声状态、当前 / 目标序号、是否保护路由）、
  `protected[]`（每条保护路由整步后是否 `audible`、通路端口 `path`、
  `viaTemporary`）、`snapshot`（该步完成后的 pairs / cables，供绘图）；
  只有两个中间快照都通声的动作次序才会出现在方案里；
- `metrics`：`plugOps`（= 2× 步数）、`removeCount` / `moveCount`（含 `parkCount`）
  / `addCount` / `tempAddCount`、`tempCableCount`、`newCableCount`、
  `reusedCableCount`；
- `reuse`：跳线复用清单 `unchanged`（保持不动）/ `moved`（一端换接）/
  `recycled`（拆下后在别处复用）/ `new`（动用新跳线）/ `removedOriginal`（完全
  拆除），每项标注源跳线编号与两端插孔；
- `temporaryCables[]`：临时跳线（展示编号 9001 起、接入 / 拆除步号、保通的保护
  路由序号）；
- `baseline` / `target`：现状与目标的 pairs / cables（含常态状态），供前后对照；
  `feedbackLoops` 为目标配置反馈环，`solverNote` 为搜索超限等说明。

400 时 `error.code` 为 `CONFIG_INVALID`（当前配置非法）、`TARGET_INVALID`
（目标配置非法；`details.conflicts` 给出目标无解路由与冲突端口，
`details.silentRoutes` 给出目标跳线就位后仍不通声的路由）、`PROTECTED_INVALID`
（保护序号越界 / 重复 / 非整数，或该路由不在目标列表）或 `REWIRE_INVALID`。
409 时响应体顶层为 `error`，完整阻塞分析直接在同体（字段：`blockers[]`、
`protectedRoutes`、`baseline`、`target`、`inconclusive`、`solverNote`），
`blockers[].type` 取值 `jack-occupied` / `must-remove-cable` /
`must-break-normal` / `no-bypass-jack` / `protected-silent-baseline` /
`goal-not-audible`。两种错误都**不包含 steps**（不产生半成品方案）。

- `POST /api/crosstalk-isolation` — 串音隔离规划，请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "isolation": {
    "groups": ["主唱", "对讲"],
    "forbiddenPairs": [["主唱", "对讲"]]
  }
}
```

`isolation.groups` 按路由顺序填写隔离组名（必须与路由数量一致；`null` / 空串
表示该路由不分组）；`forbiddenPairs` 为 `[组A, 组B]` 数组（两组都必须被至少
一条路由使用、不能自禁配，自动排序去重）。200 响应包含：

- `cables` / `steps` / `notes` / `pairs`：隔离规划后的最少跳线方案（同
  `/api/plan` 结构，含全 / 半 / 直通语义下的常态状态）；
- `routes[]`：每条路由的 `group`、`chain`（链路）、`cables`、`normalIds`、
  `component`（所属物理分量）与 `planningStep`（回溯后的实际规划步序）；
- `groups[]`：每个隔离组的 `routeIndexes` 与 `componentIds`（禁配组的分量集
  必须不相交）；
- `components[]`：承载路由的物理连通分量（`id`、`groups`、`routes`、
  `ports`、`violated`），供前端按分量着色；
- `forbiddenPairs[]`：每个声明的组对及其 `satisfied`；
- `feedbackLoops`：保留的反馈环路检测（警告）；
- `isolation`：`greedyOk`（输入顺序贪心是否已满足隔离）、`greedyCableCount`、
  `backtracked`、`routeOrder`、`searchNodes`、`truncated`、`solverNote`。

409 时（顶层 `error.code = ISOLATION_CONFLICT`，完整分析在响应体）：

- `conflicts[]`：冲突组对 `groups`、`structural`（共享设备内部 / 争用同一背板
  插孔等结构性、不可消除冲突）、`permanent`、`routesByGroup`、`message`、
  `evidence`（port/edge 交替的**最短共享证据**，每个 port 带 `jack` 与该点
  `groups`，edge 带类型与中文 label）、`permanentEvidence`；
- `unsatisfiedRoutes[]`：卷入禁配共分量的路由（`isolation-conflict`）与终止
  状态下不可路由的请求（`unroutable`，附原因）；
- `terminal`：终止搜索状态（已提交路由 / 跳线数，仅分析，非可施工方案）；
- `baseline`：输入顺序贪心对照的 `pairs` / `cables` / `components` /
  `violatedPairs` / `permanentViolatedPairs` / `unroutable`；
- `inconclusive` / `solverNote`：搜索超限时的不结论标记。
  409 响应**不含 steps**（不提交部分方案）。

- `POST /api/redundancy` — 关键路由双通道规划（主备抗单点断路），请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "redundancy": { "criticalRoutes": [0, 2], "maxNewCables": 3 }
}
```

`criticalRoutes` 为从 0 起的关键路由序号（非空、不重复、不越界）；
`maxNewCables` 为最多允许新增的跳线数（非负整数，相对输入顺序贪心基线）。
200 与 409 响应字段详见上方「关键路由双通道规划」一节；409 的错误码为
`REDUNDANCY_CONFLICT`，400 的错误码为 `REDUNDANCY_INVALID` / `CONFIG_INVALID`。

## 关键路由双通道规划（主备抗单点断路）

完成一次 **计算路由方案** 后，“9. 关键路由双通道规划”卡片出现。勾选若干
**必须抗单点断路**的关键路由，并填写**最多允许新增的跳线数**（`maxNewCables`），
点击 **🧯 计算主备双通道方案**。系统沿现有设备、插孔对与全常态 / 半常态 / 直通
语义，为**全部路由**联合选择一套**可同时安装**的通路：

- 每条关键路由得到**主通路（primary）**与**备用通路（backup）**两条逐段链路；
- **非关键路由仍需保持可用**：在最终插孔占用下其单条通路必须真实通声；
- 目标按字典序：**先满足全部路由（关键路由双通路 + 非关键路由可用）→
  跳线总数最少**（相对输入顺序贪心基线的新增跳线数不超过预算）；
- 主备两条通路**不得共用会被拔断的跳线、被切断的常态或独占插孔**：
  - 全局“一插孔一插头”保证两根跳线不能争用同一插孔（枚举与提交层强制）；
  - 备用候选直接过滤掉与主路共用常态的路径；
  - **半常态上插孔并送按最终占用判定**：上插孔插线时常态保持、信号并送，
    走常态的主路与从上插孔出跳线的备路可同时存活；下插孔插线（或全常态
    任一侧插线）使常态转为**热备**——跳线在役时走跳线，跳线被拔后插孔
    释放、常态自动恢复；切断常态时跳线仍在役；
  - 设备内部连接不属于单点故障模型（不会被拔 / 被切），主备在设备内部
    汇合允许（典型：两条通路在目标输入插孔经“常态 / 跳线”热备汇合）。

搜索为「MRV 最少候选槽位优先 × 候选通路按跳线数升序」的带回溯 DFS，
主槽先于备槽，跳线总预算从 0 起迭代加深（首个可行方案即跳线最少方案，
单条通路候选枚举上限 4 条跳线 / 40 条路径 / 12 万搜索节点，超限给
`inconclusive` 而不伪称无解）。预算不足但放宽预算可行时，409 负载带
`budgetLimited: true`。

页面输出：

- 统计条（关键路由数 / 跳线总数 / 基线跳线 / 新增跳线 / 搜索节点）与
  接线顺序、插头对常态的**并送 / 热备 / 断开**说明；
- **主备逐段链路**（主蓝、备橙；“当前通声 / 热备待用”标签与每条链路的
  热备常态编号）；
- **最终占用**：独占插孔（插孔 → 跳线）与常态连接（生效 / 热备断开、
  使用该常态的主备通路归属）；
- **主备双通道拓扑图**：主通路跳线蓝色、备用橙色、非关键灰色；绿色实线
  ＝生效常态，黄色虚线＝最终占用下的热备常态；插孔旁 **「并」** 为半常态
  上插孔并送点、**「热」** 为热备端点；
- **逐一断点故障预览**：枚举全部已安装跳线（被拔）与最终生效常态（被切），
  点击任一断点展示各关键路由“主 / 备谁幸存”、非关键路由是否失声；
  拔跳线后的常态自动恢复由后端按故障快照精确仿真。

409（`REDUNDANCY_CONFLICT`）时**不返回接线步骤、不提交部分方案**，负载含：

- `conflicts[]`：无法获得独立备用通路的关键路由，`blockers[]` 给出被迫共用的
  **冲突断点**（`normal` 共用常态 / `jack` 独占插孔 / `same-path`），
  `primaryChain` 与冲突最少的备用理想路径 `witness`（候选跳线用 9001 起的
  见证编号），另有联合占用下的 `occupiedReasons`；
- `unsatisfiedRoutes[]`：未满足路由（关键路由的主 / 备槽或非关键路由，附原因
  与冲突端口）；
- `occupiedJacks[]` / `cables`：终止搜索状态的占用插孔与跳线（仅分析）；
- `baseline`：输入顺序贪心基线的 `pairs` / `cables`；基线本身存在不可路由
  请求时带 `baselineInvalid: true`；
- `budgetLimited` / `inconclusive` / `solverNote` / `searchNodes`。

请求体：

```json
{
  "config": { "devices": [], "pairs": [], "routes": [] },
  "redundancy": { "criticalRoutes": [0, 2], "maxNewCables": 3 }
}
```

200 响应含 `cables`（每根跳线带 `routeIndex` / `role`
（primary/backup/single）与 `reusedBaseline`）、`routes[]`（关键路由带
`primary` / `backup` 两个链路对象：`chain` / `cables` / `normalIds` /
`alive` / `standbyNormals`；非关键路由带 `path`）、`baselineCableCount` /
`extraCableCount` / `maxNewCables` / `withinBudget`、`occupancy`
（`jacks` / `normals`）、`failurePreview`（`breakpoints` 排序总表 +
`breaks[]` 逐断点 `routes[].primaryAlive/backupAlive/pathAlive/survivor/
serviceLost` 与 `criticalLost` / `nonCriticalLost`）、以及 `pairs` /
`steps` / `notes` / `feedbackLoops`。



## 求解模型

- 信号沿三类边流动：设备内部（输入→输出，0 跳线）、生效的常态连接
  （上→下，0 跳线）、前面板跳线（任意空闲输出插孔 → 空闲输入插孔，1 条跳线）。
- 按用户给定顺序逐条路由求解，每条在当前插孔占用状态下用 0-1 最短路
  （Dijkstra）求最少跳线路径；已提交路由占用的常态连接受保护，
  后续跳线不得将其断开（否则该插孔对后续路由禁用）。
- 路由失败时，对照“忽略占用”的理想路径定位被阻塞的边，报告冲突端口。
- 全部提交后，在“设备内部 + 生效常态 + 跳线”有向图上做 DFS 检测反馈环路。
- 断路演练复用同一图模型：摘除断点边/插孔占用后，仅释放“使用者全部为
  受影响路由”的常态保护（仍在服役路由依赖的常态继续保护），再按原顺序
  逐条重路由；新跳线编号单调递增，避免与保留跳线冲突。
- 走线排版复用 `plan_all` 的已安装跳线，只在面板几何层做分配：列位由分区
  声明确定；同一槽层内两根跳线的 T/B 列序互逆即为一次交叉（不同层物理
  错开不计）；跳线可用槽层 = 其水平跨度所经各分区槽层集合的交集，且受
  每层每分区容量约束。槽层分配用带剪枝的精确字典序搜索
  （未分配数 → 交叉数 → 同层长度，跨区线数为固定第二键），搜索规模超
  30 万节点时回退贪心并在 `solverNote` 说明；左右绕行方向在槽层确定后
  按层独立求解（相邻列进槽对撞最少、其次反向绕行附加最短，≤16 根时
  2^k 全枚举保证最优）。残留交叉再逐根试探改层，判定是否“无法避免”。
- 命名审计在 `plan_all` 完成后的**无向**物理图（设备内部 + 生效常态 + 跳线，
  边双向）上做并查集归并；半常态上插孔插线时不断常态，因此上/下端口仍在同一
  分量，并把该插孔对识别为需要名签的分流点。别名构造「别名 → 规范名」有向图，
  Tarjan 求 SCC 检测环（环代表取环内被显式声明为规范名次数最多、并列字典序
  最小者），同一别名多个出边检测分叉；纯别名端口在唯一收敛时按目标规范名补全。
  互斥名/无标签的证据路径用**多源 BFS** 求最短（所有同名端口同时为源、所有对方
  名签端口为汇），保证给出的是两个命名端点之间跳数最少的物理路径。
  **跨路由串线与名签解耦**：另建与 `detect_loops` 同构的有向信号流图
  （设备内部 in→out、生效常态 上→下、跳线 from→to），Tarjan 求 SCC 合并互达源
  （反馈环），再沿有向边**反向**追溯到缩点图上入度为 0 的**终源 SCC**（只含
  输入端口的悬空 SCC 不产生信号，仅在整段总线无驱动时按物理分量归为一个未接线
  来源）；源端口共享同一终源即为同一真实独立信号的**同源分支**（典型：真实
  信号进入多输出设备后从两个输出分别建路由），归为一个来源、不增加串线计数；
  一个源 SCC 反向追到多个不同终源才是真正的多源混合（覆盖设备内部混合与半常态
  并送），其路由归属全部终源。即使**只规划了混合输出**（例如路由列表仅含
  MIX.out→MON.in，两个真实源分别经生效常态进入 MIX.in1 / MIX.in2），审计也会
  从该混合源反向恢复两个真实独立源，把混合输出路由同时归属两源、照常返回一条
  串线（不会因混合点自身被归为 mix 而漏报），恢复出的源作为 `sources`、混合点
  列入 `downstream`，证据端点取两终源输出端口。同一无向物理分量内出现两个不同
  终源即报串线，证据路径为两组来源代表端口之间的多源 BFS 最短路（起点按端口名
  排序入队，保证可复现），只随规划/物理连通变化。
  审计全程不修改规划状态。
- 无中断改线演练在两份 `plan_all` 结果（现状 / 目标）之间求解。物理状态只用
  **在役跳线连接集 `(tJack,bJack)`**表示：常态是否生效完全由插头占用推导
  （full：T/B 任一被插即断；half：仅 B 被插断，T 被插时信号并送）；信号通路在
  「设备内部 in→out + 生效常态 上→下 + 在役跳线 T→B」有向图上做 0-1 Dijkstra。
  动作为六类原子步（每步恰为两个插 / 拔动作）：拆线、单端换接（直接完工
  complete / 临时让位 park）、补线、临时跳线接入 / 拆除。**保护校验落在每个
  插 / 拔动作后的中间快照上**，而非宏步骤完成后的终态：中间快照用“连接集 +
  悬空单端（另一端 None 占位）+ 单插了一端、尚未成型的插头占用”表示，换接
  “先拔后插”次序唯一（悬空瞬间跳线不成回路，失声即拒绝），补线 / 拆线各枚举
  两个动作次序，只接受两个中间快照都让所有保护路由可达的次序，并把选定次序
  随路径保存、回放时逐动作复核并出中间快照。搜索为确定性 Dijkstra：
  直接完工 / 补线 / 拆线优先，只有占用插孔的电缆本身承载保护路由（不能拆）时
  才允许把它让到目标态也空闲的同型插孔（park），且孔位只取编号最小者以避免
  排列爆炸；当没有任何安全推进动作时，才用“一条候选跳线”的扩展 Dijkstra 为
  受威胁保护路由寻找**目标态空闲插孔**组成的临时旁路，临时跳线在目标连接集里
  不存在，终态自然清零。代价字典序：步数 → 动作优先级（完工 / 补线 / 拆线先于
  让位、临时旁路）→ 确定性次序，因此兼容跳线复用最多、新跳线与临时跳线最少。
  终态除连接集一致外还要求每条目标路由真实可达，防止贪心规划的连接集与逐边
  可达性不一致（如设备回环伪路径）；节点超 30 万返回 `inconclusive` 与已发现
  的阻塞点，不伪称无解。
- 串音隔离规划复用 `Solver` 的常态判定 / 最短路 / 邻居枚举，但状态改为
  不可变的搜索节点 `Node(plugs, cables, protected_normals, …)`，分支时整体
  复制。候选路径用环无关 DFS 枚举（邻居与 `Solver._neighbors` 一致，
  另需通过 `path_consistent`），按跳线数升序、有 40 条 / 6000 访问上限。
  隔离判定在无向物理图（设备内部 in↔out、生效常态 上↔下、跳线 from↔to，
  边双向）的并查集上：禁配组的路由链路端口集合根不相交。设备内部边预计算成
  不可变分量（`device_internal_components`），搜索热路径只对跳线与生效常态
  做增量并查（`fast_dsu`）。搜索为「路由顺序（输入序号优先）× 路径选择
  （跳线数优先）」两层 DFS + 预算迭代加深，保证在节点上限内找到跳线最少、
  顺序最贴近输入的可行规划；永久图（设备内部 + 跳线）共分量剪枝与剩余路由
  可通性剪枝均为安全剪枝。无解时在终止节点状态上叠加未提交路由的理想路径边
  （`build_augmented_adjacency`），再做多源 BFS 最短共享证据，恢复
  “要让两组路由同时成立就必然共分量”的结构性冲突（含两根跳线争用同一背板
  T 插孔——该插孔物理上只能插一根跳线）。
- 关键路由双通道规划在不可变搜索节点上做「MRV 槽位 × 路径选择」两层回溯 DFS
  + 跳线总预算迭代加深：每条关键路由占主 / 备两个槽位（主先备后），非关键路由
  一个槽位；候选通路复用 `isolation.enumerate_paths` 的环无关枚举（含插孔占用
  与自身一致性约束），备用候选额外排除与主路共用常态或完全相同的路径。提交时
  **不登记常态保护**——后续跳线允许以半常态并送（上插孔插线、常态保持）或
  主备热备（下插孔 / 全常态插线使常态转为待恢复）改变常态活性，常态生效与否
  一律由最终插头占用推导（`active_normal_ids`）。全部槽位落位后做终判：非关键
  路由在最终占用下必须逐段连通；关键路由在无故障时至少一条连通，并对每一根
  已安装跳线（拔线释放插孔后重算常态，全 / 半常态可能自动恢复）与每一条最终
  生效常态（强制切断）逐点仿真，要求主备至少一条幸存。无解时备用理想路径在
  空占用节点上枚举，按“共用常态 / 独占插孔 / 完全相同”提取冲突最少的见证
  （主路经常态、备路在该对端点插跳线的热备端点汇合豁免为合法），409 返回冲突
  断点、终止状态占用插孔与未满足路由，不提交部分方案。
